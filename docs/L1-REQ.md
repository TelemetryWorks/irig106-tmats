# irig106-tmats — Level 1 Requirements

> **Status: draft for review (design phase).** These requirements derive from
> `docs/USE-CASES.md` (UC-01 … UC-17), the owner's decisions recorded in
> `docs/adr/`, and IRIG 106 Chapter 9. L2 and L3 decompositions follow.

## Purpose

This document establishes the Level 1 (L1) SHALL-statement requirements for
`irig106-tmats`, a Rust library for the Telemetry Attributes Transfer
Standard (TMATS) defined in RCC IRIG Standard 106 Chapter 9, and for `tmats`,
its command-line tool (crate `irig106-tmats-cli`).

L1 requirements define **what** the product must do at the highest level of
abstraction. They are the root of the requirements tree; L2 requirements
decompose each L1 into architectural decisions, and L3 requirements decompose
each L2 into implementation-level obligations. All three levels are traced
through `docs/TRACE-MATRIX.md`.

## Scope

This document covers the library `irig106-tmats` and the CLI
`irig106-tmats-cli`, which are released together at one version from this
repository. Where a statement says "the library", it binds the library crate;
"`tmats`" binds the CLI; "the project" binds both and their release process.

Items explicitly out of scope are recorded in the **Non-Requirements** section
below. Items deferred to future releases are recorded in `docs/ROADMAP.md`
rather than in this document. The release that delivers each requirement is
named in its rationale; the roadmap, not this document, governs scheduling.

## Conventions

### Requirement identifier format

Each L1 requirement is assigned a stable identifier of the form
`L1-<CATEGORY>-<NNN>`, where `<CATEGORY>` is a code drawn from the table below
and `<NNN>` is a zero-padded sequence number within that category. Identifiers
are permanent: if a requirement is retired, its identifier is retired with it
and never reused.

L2 and L3 requirements derived from an L1 use `L2-<CATEGORY>-<NNN>` and
`L3-<CATEGORY>-<NNN>` respectively, with parent links recorded in those
documents and in the trace matrix.

Non-requirements (explicit out-of-scope items) use the prefix `NR-<NNN>`.

### SHALL language

Every requirement in this document uses the verb SHALL to express a mandatory
obligation. SHOULD, MAY, and WILL are reserved for L2/L3 derivations where
they carry their conventional meanings.

### Requirement metadata

Each requirement carries:

- **Statement** — the SHALL obligation itself
- **Rationale** — why the requirement exists, with its use case, ADR, or
  Chapter 9 source
- **Verification Method** — how compliance is demonstrated: Test (T),
  Analysis (A), Inspection (I), Demonstration (D)
- **Evidence** — for a requirement verified other than by Test, the artifact
  that carries the check (a script, a CI job); without it the requirement
  stays Draft

**Status and verification artifacts** are tracked in
[`docs/TRACE-MATRIX.md`](TRACE-MATRIX.md), regenerated by
`scripts/build-trace-matrix.py` from the `/// Requirements:` doc-comment tags
above Rust `#[test]` items and from the parent links in these documents. The
matrix is the single source of truth for live status; this file, `L2-REQ.md`,
and `L3-REQ.md` carry only spec content.

### Verification method vocabulary

- **Test (T)**: executable verification — Rust tests tagged with a
  `/// Requirements: L?-XXX-NNN` doc comment directly above `#[test]`,
  property tests, and fuzz harnesses.
- **Analysis (A)**: logical evaluation, such as static analysis or a bound
  argument, named on an Evidence line.
- **Inspection (I)**: examination of code, documents, or configuration, backed
  by an artifact named on an Evidence line (for example a CI job or a check
  script).
- **Demonstration (D)**: operational observation by a person, recorded as a
  procedure.

## L1-READ: Reading TMATS without loss

### L1-READ-001

**Statement**: The library SHALL read code-name TMATS (IRIG 106 Chapter 9 §9.4.2) from any byte sequence and SHALL retain every attribute present — known, unknown, vendor, extension, duplicate, or malformed — in input order, with its original bytes.

**Rationale**: Nothing a user wrote may be lost (UC-01, UC-14; ADR-0002). The prototype and the legacy tools dropped attributes they did not decode. Delivered in 0.1.

**Verification Method**: Test (T)

### L1-READ-002

**Statement**: The library SHALL parse each code name into its group, occurrence index, path segments, and every index, including multiple-entry indices such as those in `D-1\MN-1-2`.

**Rationale**: Chapter 9 multiple-entry items carry one or more indices (§9.4.2, Table 9-1 note); the prototype lost nested indices. Delivered in 0.1.

**Verification Method**: Test (T)

### L1-READ-003

**Statement**: The library SHALL report each problem found while reading — including a missing delimiter, an unparseable code name, a duplicate single-entry attribute, and non-ASCII bytes — as a diagnostic carrying its location, and SHALL continue reading after it; it SHALL NOT return an empty or partial document in place of diagnostics.

**Rationale**: Real TMATS is often non-conforming (UC-14); the prototype's lenient mode could return an empty document with no diagnostics. Delivered in 0.1.

**Verification Method**: Test (T)

### L1-READ-004

**Statement**: The library SHALL treat code names case-insensitively and independently of attribute order, while preserving each attribute's original spelling.

**Rationale**: "TMATS is not case sensitive" and "Attributes may appear in any order" (Chapter 9 §9.4.2). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-READ-005

**Statement**: The library SHALL recognise every attribute group defined in Chapter 9 of the baseline edition — G, T, R, M, P, D, B, S, Q, C, H, V, and X — and the `COMMENT` code name.

**Rationale**: Table 9-1 (106-23) defines thirteen groups; the prototype knew nine. `COMMENT` is defined in §9.4.2. Delivered in 0.1.

**Verification Method**: Test (T)

## L1-CH10: Chapter 10 setup records

### L1-CH10-001

**Statement**: The library SHALL accept the payload of a Chapter 10 Computer-Generated Data Format 1 (data type `0x01`) setup-record packet, decode its channel-specific data word, and read its TMATS body.

**Rationale**: Every Chapter 10 recording carries its TMATS as a setup record (UC-02). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-CH10-002

**Statement**: The library SHALL report the setup record's Chapter 10 version, its setup-record-configuration-change indication, and its body format, and SHALL report an XML body as unsupported rather than reading it as code-name TMATS.

**Rationale**: The CSDW carries these facts; XML TMATS is out of scope for now (ADR-0015, NR-001), and misreading it as code-name TMATS would produce nonsense. Bit positions are confirmed from the archived Chapter 10/11 text (ADR-0009). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-CH10-003

**Statement**: The library SHALL build a setup-record payload — channel-specific data word and TMATS body — from a document.

**Rationale**: `irig106-write` puts TMATS into recordings; the library supplies the payload and never writes packets or files itself (ADR-0010). Delivered in 0.5.

**Verification Method**: Test (T)

## L1-EDN: IRIG 106 editions

### L1-EDN-001

**Statement**: The library SHALL read TMATS of any IRIG 106 edition.

**Rationale**: The code-name syntax of §9.4.2 has not changed across editions; parsing is edition-independent (ADR-0016). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-EDN-002

**Statement**: The library SHALL determine a document's IRIG 106 edition from, in order of precedence, a caller override, the `G\106` attribute, and the Chapter 10 version in the setup-record CSDW; it SHALL report which source was used and any disagreement between sources, and SHALL report an unknown edition rather than guess.

**Rationale**: UC-04; ADR-0016. `G\106` holds "the last 2 digits of the year" (Table 9-2). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-EDN-003

**Statement**: The library SHALL validate a document against the attribute definitions of any edition from 106-04 through 106-24 Revision 1.

**Rationale**: Real recordings span every edition since Chapter 10 appeared (ADR-0016). The baseline edition (0.2–0.3) is 106-24R1; the full range is delivered in 0.4.

**Verification Method**: Test (T)

### L1-EDN-004

**Statement**: The project SHALL publish the differences in Chapter 9 attribute definitions between editions, generated from the archived Chapter 9 tables.

**Rationale**: The owner asked "can we document the deltas in all the versions?"; ADR-0016. Delivered in 0.4 as `VERSION-DELTAS.md`.

**Verification Method**: Inspection (I)

## L1-REG: Attribute definitions (registry)

### L1-REG-001

**Statement**: Every built-in attribute definition, keyword set, range, and rule SHALL cite the IRIG 106 edition and the section or table and row it comes from.

**Rationale**: The prototype's worst defects were plausible meanings written from memory (ADR-0001, ADR-0004). Delivered from 0.2.

**Verification Method**: Inspection (I)

### L1-REG-002

**Statement**: For each attribute, the library SHALL hold the Chapter 9 usage attributes — R/R Ch 10 Status, Allowed when, Required when, Links to, Links from, Range, and Default — and the editions in which the definition was introduced, changed, or removed.

**Rationale**: These seven fields are Chapter 9's own definition of each attribute (§9.5.1 a); views, links, and validation derive from them (ADR-0004, ADR-0006). Delivered from 0.2.

**Verification Method**: Test (T)

## L1-VIEW: Lookup, structured views, and links

### L1-VIEW-001

**Statement**: The library SHALL find attributes by code name and by code-name pattern (for example every `R-1\TK1-n`), returning the original value and its location.

**Rationale**: UC-03. Delivered in 0.1.

**Verification Method**: Test (T)

### L1-VIEW-002

**Statement**: For a Chapter 10 channel ID, the library SHALL present the channel's data type, data source, enabled state, and data link, and SHALL follow the links Chapter 9 defines (§9.5.1 b) to the linked format definition, its measurements, and their conversions.

**Rationale**: UC-05 — what `irig106-studio` needs for labels and what `irig106-decode` needs to decode data. Delivered in 0.2.

**Verification Method**: Test (T)

### L1-VIEW-003

**Statement**: The library SHALL report every link that cannot be resolved rather than omit it.

**Rationale**: Silent omission hides broken configurations (UC-05, UC-14). Delivered in 0.2.

**Verification Method**: Test (T)

## L1-VAL: Validation

### L1-VAL-001

**Statement**: The library SHALL validate a document against a selected edition and report findings, each with a stable rule identifier, a severity, the attribute's location, and the IRIG 106 citation of the rule.

**Rationale**: UC-06; ADR-0006. Delivered in 0.3.

**Verification Method**: Test (T)

### L1-VAL-002

**Statement**: Validation SHALL check each attribute against its usage attributes, that multiple-entry indices run from 1 to their counter "with no missing values", that every link resolves, and that every key value is unique.

**Rationale**: Chapter 9 §9.5.1 a defines the usage attributes, index contiguity, and key uniqueness ("Any attribute with a Links from: is a key and must be unique"). Delivered in 0.3.

**Verification Method**: Test (T)

### L1-VAL-003

**Statement**: The library SHALL provide a Chapter 10 recorder profile that applies the R/R Ch 10 Status rules.

**Rationale**: Chapter 9 defines these rules specifically "to support setup of a Chapter 10 recorder" (§9.5.1 a). Delivered in 0.3.

**Verification Method**: Test (T)

### L1-VAL-004

**Statement**: The library SHALL report a value longer than a recommended maximum length as a warning by default, not as an error.

**Rationale**: Chapter 9 gives some ranges as "the recommended maximum length of the value"; owner decision 2026-09-25 (UC-06). Delivered in 0.3.

**Verification Method**: Test (T)

## L1-EXT: Extensibility and the standard's extension groups

### L1-EXT-001

**Statement**: Users SHALL be able to add attribute definitions and override built-in ones without modifying the library.

**Rationale**: The owner expects users to "extend the tmats definitions or even flat out violate the standards" (UC-07; ADR-0004). Delivered in 0.3.

**Verification Method**: Test (T)

### L1-EXT-002

**Statement**: Users SHALL be able to change the severity of any rule, disable any rule, and add rules of their own.

**Rationale**: UC-07; ADR-0006. Delivered in 0.3.

**Verification Method**: Test (T)

### L1-EXT-003

**Statement**: The library SHALL group V-group attributes by data source and vendor acronym (§9.5.13) and SHALL link each X-group attribute to the attribute it extends by group, code, and leading indices (§9.5.14).

**Rationale**: The standard's own extension mechanisms (UC-08; ADR-0008). Delivered in 0.1.

**Verification Method**: Test (T)

## L1-WRT: Writing, editing, comparing, and generating

### L1-WRT-001

**Statement**: The library SHALL serialize an unedited document to bytes identical to the bytes it was read from.

**Rationale**: Byte-faithful round trips (UC-09; ADR-0002); required for `G\SHA` to remain valid. Delivered in 0.1.

**Verification Method**: Test (T)

### L1-WRT-002

**Statement**: The library SHALL normalize output — canonical order, consistent line endings, recomputed counters — only when the caller explicitly requests it.

**Rationale**: The prototype's serializer silently recomputed counters and reordered attributes (UC-09). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-WRT-003

**Statement**: The library SHALL provide edits — set, insert, remove, and renumber — that leave every byte outside the edited attributes unchanged and that keep X-group links intact through renumbering.

**Rationale**: UC-10; ADR-0007, ADR-0008. Delivered in 0.5.

**Verification Method**: Test (T)

### L1-WRT-004

**Statement**: The library SHALL NOT change a document except through an edit the caller applies; where a fix is unambiguous, a finding SHALL carry a suggested edit.

**Rationale**: No automatic repair (UC-12; ADR-0007). Counter mismatches are always reported because the declared count may be the true value. Delivered in 0.5.

**Verification Method**: Test (T)

### L1-WRT-005

**Statement**: The library SHALL compare two documents attribute by attribute, independent of order and case, reporting added, removed, and changed attributes.

**Rationale**: UC-11, including changes between setup records within one recording. Delivered in 0.5.

**Verification Method**: Test (T)

### L1-WRT-006

**Statement**: The library SHALL generate a document from a channel inventory whose content passes validation for the selected edition, reporting what the caller must still supply rather than inventing it.

**Rationale**: UC-13; the prototype's generator produced output that failed its own validator and wrote numeric codes where Chapter 9 requires keywords. Delivered in 0.5.

**Verification Method**: Test (T)

## L1-SUM: TMATS checksums

### L1-SUM-001

**Statement**: The library SHALL compute the TMATS checksum defined for `G\SHA`: SHA-256 over every byte of the TMATS except the text from `G\SHA` through the following semicolon, expressed as `2-` followed by 64 lower-case hexadecimal characters.

**Rationale**: Chapter 9 Table 9-2 (`G\SHA`, from 106-15) and Chapter 6 §6.2.3.11 f (UC-15; ADR-0014). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-SUM-002

**Statement**: The library SHALL verify an embedded `G\SHA` value and report whether it matches, does not match, is absent, names an unknown algorithm, or is malformed.

**Rationale**: UC-15; ADR-0014. Delivered in 0.1.

**Verification Method**: Test (T)

### L1-SUM-003

**Statement**: The library SHALL compute the irig106.org flex signature exactly as `irig106lib` defines it, and SHALL identify it as non-standard wherever it is presented.

**Rationale**: Compatibility with `igDisplayTMATS`; not part of IRIG 106 (UC-16; ADR-0014). Delivered in 0.1.

**Verification Method**: Test (T)

## L1-IO: Input/output boundary

### L1-IO-001

**Statement**: The library SHALL perform no file, network, or other I/O: it SHALL read from byte sequences and write to byte sequences or to writers supplied by the caller.

**Rationale**: Owner decision: "The library should not, the simple test CLI should be able to open the file" (ADR-0010). Keeps the library usable in any host. Applies from 0.1.

**Verification Method**: Inspection (I)

## L1-CLI: The `tmats` command-line tool

### L1-CLI-001

**Statement**: The project SHALL provide a command-line tool, `tmats`, that accepts either a Chapter 10 recording or a TMATS text file and determines which by content.

**Rationale**: The Rust successor to `idmptmat` (UC-17; ADR-0011, ADR-0019). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-CLI-002

**Statement**: `tmats` SHALL show TMATS in raw, tree, and channel-summary forms.

**Rationale**: `idmptmat`'s three formats (`-r`, `-t`, `-c`), which the owner wants kept (UC-17). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-CLI-003

**Statement**: `tmats` SHALL report every setup record in a recording, in file order.

**Rationale**: `idmptmat` reads only the first packet (defect D2, `docs/TEST-DATA.md`). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-CLI-004

**Statement**: `tmats` SHALL extract the TMATS bytes of a setup record to a file.

**Rationale**: UC-17; replaces the external-tool advice in `irig106-ch10-reader`'s documentation. Delivered in 0.1.

**Verification Method**: Test (T)

### L1-CLI-005

**Statement**: `tmats` SHALL compute, verify, and stamp `G\SHA`, and SHALL compute the flex signature on request.

**Rationale**: "we should add in the different signature functionality into our CLI tool" (owner; UC-15, UC-16, UC-17). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-CLI-006

**Statement**: `tmats` SHALL provide plain-text output and JSON output conforming to a published, versioned schema, and SHALL use documented exit codes.

**Rationale**: Scripts and `irig106-cli` must be able to rely on the output (UC-17; `docs/CLI.md`). Delivered in 0.1.

**Verification Method**: Test (T)

### L1-CLI-007

**Statement**: `tmats` SHALL NOT modify any input file; results that change TMATS SHALL be written to a new output.

**Rationale**: No silent change to user data (ADR-0007; `docs/CLI.md`). Applies from 0.1.

**Verification Method**: Test (T)

## L1-ROB: Robustness against arbitrary input

### L1-ROB-001

**Statement**: The library and `tmats` SHALL NOT panic, abort, or loop without end on any input bytes.

**Rationale**: Inputs come from recorders, editors, and damaged files; the legacy `idmptmat` loops forever on two or more data sources (defect D1). Applies from 0.1.

**Verification Method**: Test (T)

---

## L1-PERF: Performance

### L1-PERF-001

**Statement**: The project SHALL measure the time to read TMATS and to find every setup record in a recording with benchmarks run on synthesized and sample data, and SHALL compare the results with `idmptmat` on the same files.

**Rationale**: The owner requires "maximum performance" and efficiency; a numeric budget is set after the first measurement rather than guessed (ADR-0021). Applies from 0.1.

**Verification Method**: Inspection (I)

---

## L1-REL: Versioning and release

### L1-REL-001

**Statement**: The library and `tmats` SHALL always carry the same version, and `tmats` SHALL depend on exactly that version of the library.

**Rationale**: "we should align the CLI version with the Lib version at all times" (owner; ADR-0011).

**Verification Method**: Test (T)

### L1-REL-002

**Statement**: The library and `tmats` SHALL build with Rust 1.85 or newer.

**Rationale**: Edition 2024's minimum toolchain; the owner asked for "rust-version to the minimum version for 2024".

**Verification Method**: Inspection (I)

**Evidence**: `.github/workflows/ci.yml` job `msrv` (`cargo check --workspace --all-features` on Rust 1.85)

## Non-Requirements

These are explicitly out of scope. Each may return as a future requirement;
`docs/ROADMAP.md` records what bringing it back needs.

### NR-001

TMATS XML (Chapter 9 §9.4.3) is not read or written. An XML setup record is
recognised and reported as unsupported (L1-CH10-002). ADR-0015.

### NR-002

The Data Display Markup Language and the Instrumentation Hardware Abstraction
Language (Chapter 9 §9.6–9.7) are not supported.

### NR-003

Chapter 10 packets other than setup records, and telemetry data itself, are
not read or decoded; that belongs to `irig106-core` and `irig106-decode`.

### NR-004

No graphical interface is provided in this repository; a TMATS view belongs in
`irig106-studio`.

### NR-005

No WebAssembly bindings are provided in this repository; they may return as a
separate `irig106-tmats-wasm` crate. ADR-0015.

### NR-006

The library does not repair documents automatically. ADR-0007.
