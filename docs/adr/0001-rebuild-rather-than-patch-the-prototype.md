# Rebuild the crate rather than patch the prototype

## Context and Problem Statement

The first implementation of `irig106-tmats` (preserved at the git tag
`prototype-0`) was reviewed against IRIG 106 Chapter 9 by three independent
reviewers (`docs/research/2026-09-25-prototype-review.md`). The review found
defects that are not local bugs but consequences of the design:

- A parse followed by a serialize **loses data**: counters, some indexed
  values, attributes that match a code but have no field, and any value that
  does not parse as its typed field.
- **Code names map to the wrong meanings.** The P-group mapping is wrong on
  every one of `D1`, `D2`, `F1`, `F2`, `F3` (confirmed against the 106-23
  table text), and the tests assert the wrong meanings, so they pass.
- Lenient mode can return an **empty document with no diagnostics**.
- Validation is hand-coded per field and ignores the crate's own registry;
  the registry generated by `build.rs` is never included.
- Four of seven features did not compile; the generator's output fails the
  crate's own validator.

The root cause is one hand-written struct per TMATS group for a standard with
hundreds of attributes per group, which drift between editions.

## Decision Drivers

* Fidelity to IRIG 106 Chapter 9, with every rule citable
* No data loss on any input, conforming or not
* Nothing has been released beyond a crates.io name placeholder, so there is
  no semver obligation
* The owner's direction: "if we need to sort of start from scratch to make
  sure we do not have any hidden surprises later that is probably fine so we
  can go slow, methodical and incremental"

## Considered Options

* **Rebuild** around a lossless attribute store and a spec-driven registry,
  documentation first
* **Patch** the prototype: fix the round trip, the P-group codes, and the tests
  while keeping one struct per group

## Decision Outcome

Chosen option: **rebuild**, documentation first (use cases → architecture →
ADRs → L1/L2/L3 requirements → code).

Patching keeps the failure mode: each new edition and each attribute nobody
hand-mapped would reintroduce loss. Rebuilding costs little because nothing
depends on the prototype.

### Consequences

* Good: the new core can be lossless and spec-driven from the start (ADR-0002,
  ADR-0004).
* Good: the prototype remains available at `prototype-0` for reference and
  comparison.
* Bad: no working library until the 0.1 release; consumers (`irig106-studio`,
  `irig106-ch10-reader`) wait longer.
* The prototype's source is removed from `main` when the first redesigned
  code lands; until then it is marked "prototype" in `docs/PROJECT_STRUCTURE.md`.
